# FAQ (`faq`)

https://valkey.io/topics/faq/

Mostly inherited Redis-era text with stale numbers. Most important fix: the replica key-count answer explains the difference with a mechanism Valkey 9.1.2 does not use. Replicas load expired keys from the RDB.

## Findings

### F1 [minor] INACCURATE: Replica key-count explanation is wrong (`topics/faq.md:125`)
**Doc says:**
> * The RDB file will not include keys already expired in the primary but which are still in memory.
> ...
> * When the replica reads the RDB file generated by the primary, this set of keys will not be loaded.

**Problem:** The primary writes every key to the RDB, expired or not, and a replica loads all of them. Only a primary skips expired keys, and only when it loads an RDB itself (for example at startup). A replica keeps logically expired keys until the primary sends `DEL`, so replica counts are not systematically lower for the stated reason.
**Evidence:** `valkey@9.1.2:src/rdb.c:1439-1440` saves every key without an expiry check:
```
expire = objectGetExpire(o);
if ((res = rdbSaveKeyValuePair(rdb, &key, o, expire, dbid, rdbver)) < 0) goto werr;
```
`valkey@9.1.2:src/rdb.c:3497-3499,3529`:
```
 * an RDB file from disk, either at startup, or when an RDB was
 * received from the primary. In the latter case, the primary is
 * responsible for key expiry. If we would expire keys here, the
...
} else if (iAmPrimary() && !(rdbflags & RDBFLAGS_AOF_PREAMBLE) && expiretime != -1 && expiretime < now) {
```
Live 9.1.2: 100 keys with `PX 100` plus 50 persistent keys, active expire off on the primary, wait 1s, then `REPLICAOF`:
```
primary dbsize: 150
replica dbsize: 150
db0:keys=150,expires=100,avg_ttl=0,keys_with_volatile_items=0
* Done loading RDB, keys loaded: 150, keys expired: 0, all fields expired hashes: 0.
```
**Fix:** Replace the bullets with: "Replicas never expire keys on their own. The primary expires keys and sends a `DEL` to its replicas. The primary includes logically expired keys in the RDB it sends during full sync, and the replica loads all of them. So at any moment `DBSIZE` and `INFO keyspace` on the primary and replica can differ by the keys that are logically expired but not yet deleted on one side. Reads on a replica still treat those keys as missing. See [Replication: how Valkey replication deals with expires](replication.md)." Link to the section at topics/replication.md:393 instead of re-explaining it.

### F2 [minor] OUTDATED: Memory footprint numbers are stale (`topics/faq.md:25`)
**Doc says:**
> * An empty instance uses ~ 3MB of memory.
> * 1 Million small Keys -> String Value pairs use ~ 85MB of memory.
> * 1 Million Keys -> Hash value, representing an object with 5 fields, use ~ 160 MB of memory.

**Problem:** These are Redis-era figures. Valkey 8's new hashtable with embedded keys cut per-key overhead, so all three numbers are high. The page also does not say which metric (`used_memory` or RSS) or which version.
**Evidence:** Live 9.1.2, 64-bit, jemalloc:
```
empty:                         used_memory:1163464   (1.1 MB; used_memory_rss 8 MB)
DEBUG POPULATE 1000000 key 10: used_memory_human:55.90M
1M HSET h:<i> with 5 short fields: used_memory_human:134.65M
```
**Fix:** "Measured with Valkey 9.1 on 64-bit Linux, `used_memory` from `INFO memory`: an empty instance uses about 1 MB. 1 million small string keys and values use about 56 MB. 1 million hashes with 5 small fields each use about 135 MB. Figures vary with key and value sizes and the allocator."

### F3 [minor] INACCURATE: 2^32 key and element limits are not real limits (`topics/faq.md:113`)
**Doc says:**
> Valkey can handle up to 2<sup>32</sup> keys, and was tested in practice to handle at least 250 million keys per instance.
>
> Every hash, list, set, and sorted set, can hold 2<sup>32</sup> elements.

**Problem:** The keyspace, hash, set, and sorted set all use `hashtable`, which counts with `size_t`, and lists count with `unsigned long`. On 64-bit builds none of them caps at 2^32. (`intset` uses `uint32_t`, but sets convert to a hashtable long before that at `set-max-intset-entries`.) The "250 million keys" test is an unsourced Redis claim.
**Evidence:** `valkey@9.1.2:src/hashtable.h:124`: `size_t hashtableSize(const hashtable *ht);`. `valkey@9.1.2:src/hashtable.c:311`: `int8_t bucket_exp[2];      /* Exponent for num buckets (num = 1 << exp). */`. `valkey@9.1.2:src/quicklist.h:110`: `unsigned long count;`. `valkey@9.1.2:src/server.h:1523-1525`: `typedef struct zset { hashtable *ht; zskiplist *zsl; }`.
**Fix:** "There is no practical fixed limit on the number of keys or on the number of elements in a hash, list, set, or sorted set on 64-bit builds. Counts are stored as 64-bit integers. The real limit is available memory." Drop the 250 million sentence unless someone has a Valkey measurement to cite.

### F4 [minor] INACCURATE: overcommit_memory=0 behavior misdescribed (`topics/faq.md:82`)
**Doc says:**
> so if the `overcommit_memory` setting is set to zero the fork will fail unless there is as much free RAM as required to really duplicate all the parent memory pages. If you have a Valkey dataset of 3 GB and just 2 GB of free memory it will fail.

**Problem:** On current kernels, mode 0 rejects only allocations larger than total RAM plus swap, not larger than free RAM. The 3 GB / 2 GB-free example does not fail by itself. The real risks are mode 2 (strict accounting) and the OOM killer under mode 0 when copy-on-write pages grow. The short answer also uses a non-persistent `echo`, while topics/admin.md:14 gives the persistent `sysctl` form.
**Evidence:** Linux `Documentation/mm/overcommit-accounting.rst`: "0 Heuristic overcommit handling. Obvious overcommits of address space are refused." Linux `mm/util.c` `__vm_enough_memory`:
```
if (sysctl_overcommit_memory == OVERCOMMIT_GUESS) {
	if (pages > totalram_pages() + total_swap_pages)
		goto error;
	return 0;
}
```
**Fix:** Short answer: "Set `vm.overcommit_memory = 1` in `/etc/sysctl.conf` and run `sysctl vm.overcommit_memory=1`." Replace lines 81-86 with: "Because all pages could in theory change while the child is saving, the kernel's overcommit policy decides whether the fork is allowed. With mode 2 (strict), and with mode 0 on hosts with little RAM plus swap, the fork can fail even though copy-on-write means the child usually needs only a fraction of the parent's memory." Remove the ":)".
